# Контракты данных и интеграций Chronicle

## Сессии и API

Приватные API используют NextAuth v4, Google OAuth и серверные сессии PostgreSQL. Идентификатор владельца берётся только из сессии. Папка, задача, заметка, привычка, попытка и челлендж проверяются на принадлежность пользователю. Подмена чужого ID возвращает 404. Некорректный ID возвращает 400.

Успешный GET списка возвращает JSON-массив, создание/изменение — объект сущности, удаление — `{ "ok": true }`. Ошибки имеют вид `{ "error": "…", "code": "…" }`; 409 заметки дополнительно содержит актуальную версию. Клиент проверяет HTTP-статус. Ответы с пользовательскими данными имеют `Cache-Control: no-store, private`.

Изменяющие браузерные запросы проверяют `Origin` против `NEXTAUTH_URL`. При отсутствии Origin требуется `Sec-Fetch-Site: same-origin`. JSON-запросы ограничены по размеру, включая потоковое чтение: 8 KiB для задач/папок/профиля, 4 KiB для служебных действий, отдельные лимиты у заметок. Пользовательские строки не интерполируются в SQL. SQL-ошибки не возвращаются клиенту.

Папки имеют `entity_type: task | note`; GET `/api/folders?type=note`. Создание принимает `entity_type` или совместимое `entityType`; `emoji` или `icon`. Удаление папки переносит записи в раздел без папки. Версия заметки при этом увеличивается, чтобы старый черновик не восстановил удалённую папку.

Задачи используют `due_date: YYYY-MM-DD | null`, `due_time: HH:mm | null`, `priority: low | medium | high`, `completed: boolean`, `folder_id: integer | null`. Поле `status` синхронизируется с `completed` (`todo`/`done`) для совместимости бота. Отмена даты удаляет время. Время без даты не принимается. Изменение срока сбрасывает флаги напоминаний; повтор того же срока их не сбрасывает.

## Профиль и действия с аккаунтом

- `GET /api/profile`: `{user,settings,stats,telegram}`. User содержит `id,name,email,image,avatar_id,google_image,created_at`; OAuth-токены и данные сессии не возвращаются.
- `PATCH /api/profile`: частичное `{name,avatar_id,settings}`; ответ — полный профиль. Аватары `blue`, `green`, `purple`, `orange`; `null` возвращает фото Google.
- `settings`: `theme: light|dark|system`, `language: ru|en`, IANA `timezone`, `animations: boolean`, `reduce_transparency: boolean`. Настройки объединяются с существующими в PostgreSQL. По умолчанию UTC, системная тема, RU, анимации включены, уменьшение прозрачности выключено.
- `DELETE /api/profile/sessions`: завершает другие сессии, сохраняя сессию из текущего cookie.
- `GET /api/profile/export`: согласованный JSON-снимок своих данных в транзакции repeatable read. Включает старые данные удалённого раздела питания/веса, если таблицы существуют. Не включает accounts, sessions, verification tokens, токены Telegram, chat ID и секреты.
- `DELETE /api/profile/account`: `{confirmation:"DELETE"}` и Google-вход в последние 10 минут в текущей сессии. Иначе 403 `REAUTHENTICATION_REQUIRED`. Переход к Google с `prompt: login`, возврат в профиль и повторное явное подтверждение. У старых мигрированных сессий `authenticated_at=NULL`, поэтому они требуют повторного входа. Продление сессии не продлевает этот срок.

Удаление аккаунта удаляет его данные, включая сохранённые исторические данные питания/веса. Автоматические миграции такие данные не удаляют. Email показывает способ входа Google; произвольное изменение email/пароля не поддерживается.

XP вычисляется на сервере из текущего состояния: завершённая задача = 10/25/50 по приоритету, успешная отметка привычки = 15, успешный день челленджа = 20. Отмена или удаление убирает вклад. Повтор того же запроса, двойное нажатие, выполнение → отмена → выполнение не накапливают дополнительные баллы. localStorage не является источником XP.

## Telegram: контракт внешнего бота

В репозитории находится сервер Chronicle, но не отдельное приложение Telegram-бота. Наличие настроек не доказывает доставку сообщений. Для подключения нужны `TELEGRAM_BOT_TOKEN`, `TELEGRAM_BOT_USERNAME` и общий `TG_WEBHOOK_SECRET` на сервере и боте.

`GET /api/profile/telegram` возвращает `connected`, `configured`, `bot_username`, `reminders_1h`, `reminders_1d`. `connected` означает наличие подтверждённой записи в БД; открытие ссылки не меняет это состояние. `configured` означает наличие обязательных переменных окружения, а не внешнюю проверку токена.

`POST /api/profile/telegram` выдаёт `{url,expires_at}`. Ссылка: `https://t.me/BOT?start=link_TOKEN`. Случайный токен имеет срок 10 минут и хранится только как SHA-256. Новая ссылка аннулирует предыдущую ссылку пользователя.

После команды `/start link_TOKEN` бот отправляет серверный запрос:

```http
POST /api/tg-webhook
Content-Type: application/json
x-webhook-secret: SHARED_SECRET

{"action":"account_linked","chat_id":"TELEGRAM_CHAT_ID","token":"TOKEN"}
```

Допустим также token с префиксом `link_`. Сервер атомарно потребляет токен и связывает chat ID с его владельцем. Просроченный/повторный токен — 410; chat ID, уже связанный с другим аккаунтом, — 409. Бот должен доверять только ответу `{ok:true,connected:true}`. Токен и shared secret нельзя писать в логи или отдавать в публичные сообщения.

Сохранены действия существующего webhook:

```json
{"action":"task_created","chat_id":"123","event_id":"telegram-update-1001","task":{"title":"Прогулка","due_date":"2026-10-02","due_time":"18:30","priority":"medium"}}
{"action":"task_updated","chat_id":"123","event_id":"telegram-update-1002","task":{"id":42,"completed":true}}
{"action":"task_deleted","chat_id":"123","event_id":"telegram-update-1003","task":{"id":42}}
```

`event_id` — обратно совместимое необязательное дополнение. Бот должен передавать уникальный стабильный ID события и повторять его при сетевом повторе: сервер сохранит первый результат в той же транзакции и вернёт его повторно. Старые события без ID продолжают приниматься, но повтор `task_created` без ID создаёт новую задачу. Удаление отсутствующей/чужой задачи теперь возвращает 404; обработайте это явно в старом боте. Остальные ошибки валидации возвращают 400, неверный secret — 401, неподключённый/неоднозначный chat ID — 404.

`PATCH /api/profile/telegram` меняет `{reminders_1h,reminders_1d}` только у подключённого аккаунта. `DELETE` отключает бота и аннулирует непотреблённые ссылки. При исторических дублирующихся связях chat ID webhook не выбирает произвольного владельца: пользователь должен отключить старую связь и подключиться заново.

## Telegram: планировщик напоминаний

Планировщик вызывает `GET /api/cron/notify` с заголовком `Authorization: Bearer CRON_SECRET`. Пустой CRON_SECRET не даёт доступ. Рекомендуемый интервал — каждые 15 минут. Поддержка cron зависит от хостинга/тарифа; этот репозиторий не включает фиктивный запущенный планировщик.

Дедлайн вычисляется PostgreSQL из даты + времени + IANA-пояса пользователя. Для задачи без указанного времени применяется **09:00 в часовом поясе пользователя**. Напоминание за час отправляется для ближайшего часа; за день — для промежутка больше часа и до 24 часов. Просроченные задачи не рассылаются. Строки блокируются через `FOR UPDATE SKIP LOCKED`, поэтому параллельные cron-вызовы не доставляют одну запись одновременно.

Текст отправляется без HTML/Markdown-разметки: пользовательский заголовок не становится тегом. HTTP-успех и `ok:true` Telegram обязательны. Только после подтверждения выставляется флаг; ошибка оставляет возможность повтора. Каждое подтверждённое сообщение фиксируется в отдельной транзакции. Вызов ограничен 20 напоминаниями каждого типа и временным бюджетом около 45 секунд (+ текущий HTTP-запрос).

Telegram Bot API не предоставляет idempotency key для sendMessage. Редкий сбой процесса/БД между внешним подтверждением и фиксацией транзакции может привести к повтору; гарантировать exactly-once здесь нельзя. Если планировщик долго не работал и срок уже прошёл, пропущенное напоминание не отправляется задним числом.

## Миграции и сохранность

`npm run migrate` читает нумерованные `migrations/*.sql`, проверяет SHA-256, выполняет новые файлы под транзакционной advisory-блокировкой и сохраняет `schema_migrations`. Повторный запуск пропускает применённые файлы. Изменение уже применённого файла считается ошибкой: восстановите его и добавьте следующую миграцию.

`001_core.sql` создаёт основную схему и исправляет отсутствовавшие поля. Смешанную старую папку разделяет: оригинал сохраняет задачи, копия с тем же именем получает заметки. Папки только с заметками получают тип note. Старые пустые папки сохраняются. `002_notes.sql` безопасно переносит текст в JSON-документ редактора. `003_challenges_habits.sql` добавляет попытки, уникальные дневные отметки и расписания. Пользовательские таблицы не DROP/TRUNCATE. PostgreSQL DATE возвращается как YYYY-MM-DD, без преобразования календарной даты в UTC-инстант.

Перед применением к существующей БД сделайте резервную копию и прогоните миграции на восстановленной копии. Перед релизом запустите isolated DB tests; тесты не должны использовать production DATABASE_URL. Изменения схемы не выполняются из обработчиков запросов.
